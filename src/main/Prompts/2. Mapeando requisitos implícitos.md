# 2. Mapeando requisitos implícitos

## Prompt de IA:

### Pergunta:
Faça uma entrevista comigo para tirar dúvidas sobre o funcionamento do sistema, Leia as documentações gerais na pasta @docs se pense no que está faltando de informação sobre o sistema de maneira técnica mas também de produto

### Resposta 01:
Sobre o cancelamento e estoque só pode ser restaurado se o pedidio não foi marcado como enviado e ainda estava em separação ou aguardando pagamento.
Não fazemos cancelamento parcial dos itens, isso deve ser proibido.
Sobre o Multi-tenancy, não vamos trabalhar com isso nesse projeto, teremos uma única loja com todos os produtos e clientes, então podemos desfazer isso

### Resposta 02:
Isso temos pendinf, paid, packing, shipped, delivered e sim o usuário deveria marcar como recebido, mas os outros status devem ser alterados pelo admin

### Resposta 03:
pro pagamento o front-end deve chamar a rota de confirmação

Usuário não pode deletar a própria conta, só admin faz isso sim, usuário pode alterar a própria senha estando logado

### Resposta 04:
A categoria não tem limites de profundidade
Sim, um produto pode estar em mais de uma categoria e sim, quando desativado ele sai imediatamente do catalogo publico

A listagem de pedidos mostra todos, sem filtro
O admin não tem essa rota de ver pedidos de um usuário

Sim, o endereço de entrega deveria ser uma entidade que compõem Order

### Resposta 05:
Não consigo continuar a entrevista. Pegue o que discutimos e salve nos arquivos globais do projeto na pasta @docs

### Resposta 06:
aproveite e já atualize os readme de cada modulo com suas regras próprias
